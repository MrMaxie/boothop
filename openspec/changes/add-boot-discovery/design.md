## Context

The executable has no boot discovery implementation. Firmware entries and bootloader menu entries can identify different stages of the same boot path.

## Decisions

- Implement read-only adapters for UEFI, Windows Boot Manager, GRUB, and systemd-boot. Each adapter returns its source, native identifier, label, known location, current-system evidence, and selection capability.
- Expose a stable, source-qualified identifier derived from the native identity. Never use the current row number or a display name as the identity. The reboot command resolves identifiers against fresh discovery.
- Default output contains target ID, label, and a current marker when established. Show a concise availability reason if a discovered target cannot currently be selected. `-v` adds bootloader and location. `-vv` adds relevant source and detection diagnostics.
- Retain distinct selectable entries with duplicate labels. Do not collapse different boot paths based on a shared OS name. A discovered loader entry is not proof of a successful future boot.
- Read GRUB configuration as data, including menu nesting. Never execute configuration scripts to discover entries. Record unsupported syntax as incomplete discovery with a reason.
- Account for bootloader entries nested behind a firmware entry. Pass the resolved boot path to the reboot planner, which owns the necessary one-shot changes.
- Treat access failures as partial or failed discovery with explicit reasons. Adapter implementation gaps cannot satisfy the required platform coverage.
- On Windows, enumerate partition offsets, sizes, logical sector sizes, and identities with the existing PowerShell storage adapter. Open physical disks with read-only handles and expose bounded, aligned partition windows to Cargo filesystem readers: ext4-view for ext2/3/4, ferrosys for Btrfs, and fstool for XFS. The source interface cannot forward writes. Unsupported formats and features remain explicit inspection failures when recognized.
- Read fixed boot configuration locations, including Btrfs subvolume roots and symbolic links. Bound raw I/O, file size, directory size, subvolume count, and link traversal. Include partition, filesystem, subvolume, and file identity in target IDs. Raw discovery does not modify GRUB environments; menu entries without a verified writable selection path remain unavailable for direct selection, while their independent UEFI loaders remain discoverable.

## Verification

Use synthetic firmware records and bootloader fixtures for both hosts, including nested menus, identical labels, missing disks, malformed records, access denied, and changed IDs. Follow the simulation-only boundary in `add-cli-foundation`. Actual bootability is checked manually by the user after implementation.

Raw reader tests use compressed synthetic images generated by mkfs tools into newly created regular files, never mounted. The same images are read on Windows and Linux. Cover ext2/3/4, XFS, Btrfs subvolumes and compression, symlinks, partition bounds, rejected writes, malformed signatures, and identity stability. Production host adapters remain excluded from unit test builds.
