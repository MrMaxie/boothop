## Context

Discovery produces source-qualified target IDs. Restart may require selecting both a firmware entry and a nested bootloader entry. Changing those selections and requesting shutdown are separate operations that can fail independently.

## Decisions

- Parse `reboot <id> [--timeout <seconds>] [--force | --force-after <seconds>] [--yes]`. Use nonnegative whole seconds for timeout, defaulting to zero, and positive whole seconds for force-after. Reject conflicting force modes and durations the selected backend cannot represent before mutation.
- Resolve the target afresh and preflight permissions, the complete boot path, and the selected shutdown mode. Obtain confirmation before writing boot state or initiating shutdown. After an optional countdown, revalidate the target and capabilities before committing the operation.
- Prefer a native Windows dialog and an available native desktop dialog mechanism on Linux. Detect any external dialog dependency through the shared detector. If unavailable, prompt in an interactive terminal. Default to cancellation. Without either interaction mechanism require `--yes`.
- The default prompt asks only whether to restart into the chosen OS. Describe a nonzero delay relative to confirmation and warn about unsaved work when forced closure is selected. Keep backend names and raw diagnostic state out of the prompt.
- On Windows, use TaskDialog with Common Controls v6 and PerMonitorV2 DPI awareness. Present Restart and Cancel buttons with Cancel selected by default. A separate windowless shortcut launcher forwards arguments to the adjacent CLI with CREATE_NO_WINDOW, preserves confirmation, and displays failures in a native dialog. The CLI retains its normal console behavior.
- Preserve persistent boot order and defaults. Use one-shot mechanisms for UEFI BootNext, Windows Boot Manager boot sequence, GRUB next entry, and systemd-boot one-shot entry. Validate any firmware-to-loader chain before mutation.
- Record previous one-shot values and each completed write. On cancellation before shutdown or a rejected restart request, restore completed writes in reverse order when possible. Restore only values still owned by this operation so concurrent changes are not overwritten. Report incomplete recovery with the affected target state and an actionable recovery instruction.
- Accepting a restart request is the point after which the command cannot promise cancellation or recovery. A successful API response means the OS accepted the request, not that the destination OS has booted.
- `--timeout` is a cancellable delay after confirmation and before starting shutdown. `--force` still observes that delay. `--force-after` starts its clock when graceful shutdown is initiated, not during the preceding countdown.
- Windows exception approved for `--force-after`: a temporary LocalSystem service requests application closure in logged-on sessions, then waits the requested interval and calls the Windows forced restart API. Service and filesystem shutdown begin with that final request. This avoids attempting a second shutdown while an interactive graceful shutdown is already blocked. The helper remains independent of the CLI and user sessions; confirmation describes this application grace period.
- OpenRC exception approved for native openrc-init and BusyBox: an OpenRC-supervised helper requests user-process termination, retains the grace timer independently of the CLI, terminates remaining selected processes, and then invokes the normal OpenRC restart procedure. Do not terminate system services during the application grace period or use a raw reboot syscall. Compatible SysVinit retains its init-owned timing backend.
- Forced closure uses the OS shutdown procedure to close blocking applications. Raw reboot syscalls or reset mechanisms that bypass filesystem flushing are outside this mode.
- Implement platform-owned escalation that remains effective after terminal or session teardown. A timer in the ordinary CLI process is insufficient. Prove this through backend contracts and lifecycle simulations for Windows, systemd, and OpenRC. An unavailable implementation remains an open task and cannot be marked complete by adding an unsupported warning.
- Detect and authorize any required helper before selecting the boot target. Remove temporary operation resources when cancelled or rejected and ensure retrying an operation cannot leave multiple active escalation requests.

## Verification

Tests use simulated boot stores, shutdown adapters, confirmation responses, and a controlled clock. Cover staged write failures, concurrent changes, cancellation, denied permissions, and CLI process termination before escalation. Agent and CI must never execute the production application or real shutdown/boot mutations. The user manually verifies actual target boots and shutdown timing after implementation.
